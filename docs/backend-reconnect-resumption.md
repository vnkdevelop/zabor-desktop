# Восстановление сессии при переподключении — рекомендация к редизайну бекенда / Backend reconnect resumption

> Редакция от 25 сентября 2026 года.
> **Статус: РЕКОМЕНДАЦИЯ. НЕ РЕАЛИЗОВАНО.** Документ описывает предлагаемый будущий редизайн серверной части, а не текущее поведение системы. Пока он не внедрён, действует модель из раздела 1. Русская версия является основной.

Документ предназначен для владельца как проект решения. Правки продакшн-бекенда в рамках текущей задачи не вносились; здесь зафиксированы архитектура, требования безопасности и перечень документов, которые придётся синхронизировать в момент фактического внедрения.

---

## 1. Текущее поведение (констатация, соответствует коду)

Модель аутентификации — **посоединённая, в памяти**: `UserService` (singleton) держит отображение `ConnectionId → User`. Особенности:

- Нет JWT/bearer-токенов, нет атрибута `[Authorize]`, нет `accessTokenFactory`, нет серверного `WithStatefulReconnect`.
- Идентичность создаётся в `Login`/`Register`, живёт в памяти соединения, уничтожается в `OnDisconnectedAsync` (`RemoveConnection`).
- Каждый метод хаба начинается с `GetUserByConnectionId(Context.ConnectionId)` и рано выходит при `null`.
- `withAutomaticReconnect` на клиенте выдаёт **новый** `ConnectionId`. Старый принципал уже удалён → сервер не знает новый сокет → любой вызов вернул бы `null`. Поэтому полный повторный `Login` в `onreconnected`/`attemptAutoLogin` **обязателен и корректен**.
- Гонка переподключения обезврежена серверным guard'ом `isPrimary = primaryConnId == Context.ConnectionId`: устаревший `OnDisconnectedAsync` не рушит новую сессию.

Вывод: при нынешнем сервере «бесшовное» восстановление клиентскими правками невозможно. Частичный выигрыш времени переподключения уже получен на клиенте (телеметрия `reportTimeZone` больше не блокирует загрузку данных).

## 2. Проблема

Полный повторный `Login` при каждом сетевом провале:

- Повторно проверяет пароль (лишняя работа на латентно-чувствительном пути).
- Заново рассылает снапшоты состояния и перестраивает членство в канале.
- На короткой «мобильной яме» рвёт голос и членство, хотя пользователь фактически не уходил.

Цель редизайна — восстановить живую сессию без пароля и без разрыва голоса на коротких обрывах, не ослабляя текущих гарантий безопасности.

## 3. Предлагаемая архитектура

### 3.1. Resumption-токен

- В `Login`/`Register` сервер дополнительно выдаёт короткоживущий подписанный токен восстановления.
- Подпись — HMAC-SHA256 серверным секретом. **Секрет берётся только из переменной окружения** (например, `ZABOR_RESUME_SECRET`); значение секрета в репозитории и в этом документе не хранится и не воспроизводится. При отсутствии переменной путь восстановления выключен (fail-closed), система работает по модели раздела 1.
- Полезная нагрузка: `userId` + `exp` (короткий TTL, ориентир 5–15 минут) + одноразовый `nonce`. Без пароля и без иных секретов пользователя.
- Клиент держит токен в памяти рядом с `credentialsRef`, не пишет на диск.

### 3.2. Восстановление без пароля

- Клиент передаёт токен через `accessTokenFactory` (или первым вызовом сразу после `onreconnected`).
- В `OnConnectedAsync` при валидном токене сервер перестраивает `ConnectionId → User` и восстанавливает членство в канале **без** полного `Login`: без повторной проверки пароля и без лишней повторной рассылки снапшотов там, где состояние не менялось.
- При невалидном/просроченном токене — откат к полному `Login` (текущее поведение), не ошибка.

### 3.3. Disconnect-grace

- В `OnDisconnectedAsync` не рвать голос и членство немедленно: помечать пользователя `reconnecting` и запускать таймер (ориентир 10–30 с).
- Переподключение тем же токеном в окне грейса → отмена teardown и ре-байнд нового `ConnectionId` к живой сессии (без `LeaveCurrentVoice`, без лишних рассылок).
- Грейс истёк → выполняется текущий teardown.
- Guard `isPrimary` сохраняется без изменений: ре-байнд обновляет `primaryConnId`, устаревший disconnect по-прежнему не трогает активную сессию.

### 3.4. Опционально: stateful reconnect

- Серверный `.WithStatefulReconnect()` + клиентский `withStatefulReconnect: true` — переживание in-flight сообщений на коротких обрывах.
- Внедряется отдельно и только после базовых пунктов 3.1–3.3; повышает `MaximumParallelInvocationsPerClient`-давление, требует отдельной проверки нагрузки.

## 4. Безопасность

- Токен неподделываем (HMAC/JWT, секрет из env), короткий TTL, жёстко привязан к `userId`.
- Токен не заменяет пароль: он лишь продлевает уже установленную сессию в узком окне. Компрометация токена ограничена его TTL и областью (один `userId`).
- Хранение только в памяти клиента; не логировать значение токена на сервере и не выводить его в детальных ошибках.

## 5. Совместимость с фильтрами

- Путь восстановления совместим с `ClientAttestationFilter` и `AuthThrottleFilter`.
- Восстановление по токену **не** должно засчитываться как password-fail в `AuthThrottleFilter` (иначе легитимные переподключения набивают счётчик блокировок), но остаётся rate-limited по валидности токена.
- Гонку-guard `isPrimary` не ослаблять.

## 6. Stale-Docs при фактическом внедрении

Внедрение меняет модель доверия и состав серверных данных сессии, поэтому **в том же изменении** обязательны:

- `PRIVACY.md` (разд. 3 — новые данные/токен сессии на сервере; разд. 4 — сроки/грейс).
- `docs/chat-data-flow.md` (новый артефакт — токен восстановления, окно грейса, изменения маршрута сигнализации при ре-байнде).
- При изменении криптомодели/вывода ключей — `CRYPTO-NOTICE.md`.
- Обновить дату редакции; русская версия первична; менять RU и EN только вместе.

Пока редизайн не реализован, этот пункт не активен: документ не описывает текущее поведение и не заявляет защит, которых код не даёт.

## 7. Клиентские точки интеграции (на будущее)

- Хранение токена — рядом с `credentialsRef` в `signalr.ts` (только память).
- Передача — `accessTokenFactory` в конфигурации `HubConnectionBuilder`, либо первый вызов в обработчике `onreconnected`.
- В `attemptAutoLogin`/`onreconnected`: сперва пробовать восстановление по токену, при неуспехе — существующий полный `login()`.
