# Переход Electron → native: данные, версии и имена

Редакция: 2026-11-12. План, а не выполненная миграция. Текущее состояние
клиента и все незакрытые гейты — в
[native-parity-2026-11-12-continuation.md](native-parity-2026-11-12-continuation.md).

## 1. Что уже существует и не должно смешиваться

| Клиент | Профиль в `%APPDATA%` | Идентичность |
| --- | --- | --- |
| Electron stable | `zabor-desktop` | `com.zabor.desktop`, `ZABOR.exe` |
| Electron beta | `zabor-desktop-beta` | `com.zabor.desktop.beta`, `ZABOR-Beta.exe` |
| native beta | `zabor-desktop-native-beta` | не публикуется |
| native developer | `zabor-desktop-native-dev` | только `--developer`, не релиз |
| старый код | `legacy/zabor-electron-c5d07348.zip` | архив-эталон |

Три независимых профиля — это защита: установка, запуск и удаление одного
клиента не меняют данные другого. Правило сохраняется до самого перехода.

## 2. Целевое состояние (то, что просил владелец)

- ZABOR — нативное приложение на Rust, без суффиксов `beta`/`rust` в имени,
  версии идут тем же продуктовым потоком, что и раньше (`3.8.x`, `3.9.x`, …).
- Один продуктовый профиль `zabor-desktop`, один appId `com.zabor.desktop`,
  один исполняемый файл `ZABOR.exe`, одно значение автозапуска `zabor`.
- Electron остаётся только в `legacy/` как эталон и средство отката.

Суффиксы убираются **не в этой итерации**: сначала должны закрыться подписи,
updater, физическая приёмка и миграция данных. Иначе появится «стабильный»
клиент, который не умеет обновляться и не принимается сервером.

## 3. Буферная версия

Прямой прыжок «Electron stable → native stable» небезопасен: у них разные
форматы истории, ключей, файлов и сессии. Предлагается буферная версия.

### Этап A. Electron-буфер (последний Electron-релиз)

1. Добавить в Electron явный экспорт профиля в документированный пакет:
   история, `chat-files`, `chat-identity` (в защищённом виде), настройки,
   отметки прочтения, достижения. Экспорт — по действию пользователя, с
   показом состава и срока.
2. Проверить, что экспорт не меняет рабочий профиль и не удаляет данные.
3. Оставить updater Electron только для Electron: он не должен предлагать
   native как обновление.

### Этап B. native-импорт (первый native-релиз с тем же номером версии)

1. В native добавить **UI-сценарий** импорта: выбор пакета, показ состава,
   подтверждение, прогресс, отчёт. Сейчас это только CLI
   (`--import-profile`), для пользователя этого недостаточно.
2. Импорт сохраняет прежние правила: отдельный beta/целевой профиль,
   owner-bound ключи под DPAPI, журнал, откат в quarantine, отсутствие
   автоматического слияния.
3. После успешного импорта native открывает данные и работает штатно;
   Electron-профиль остаётся нетронутым.

### Этап C. Смена идентичности

Только после A+B и приёмки:

1. native получает продуктовый профиль `zabor-desktop` и appId
   `com.zabor.desktop`, версия — следующий обычный номер без суффиксов.
2. Установщик Electron и native не должны существовать одновременно с одним
   appId: сначала удаление Electron (данные уже перенесены и проверены),
   затем установка native, либо явная замена «поверх» с проверкой версии.
3. Значение автозапуска меняется с `zabor-native-beta` на `zabor`; старые
   значения удаляются установщиком, а не «сами».
4. Каналы: `stable` — обычные версии, `beta` — предрелизы. Суффикс `-rust`
   в версии не используется.

### Этап D. Откат

- До закрытия приёмки Electron-установка остаётся рабочей и обновляемой.
- native-данные при откате не удаляются: профиль можно сохранить или
  перенести в quarantine штатным rollback.
- `legacy/zabor-electron-c5d07348.zip` остаётся навсегда; удаление Electron
  из репозитория не заменяет приёмку native.

## 4. Что нужно поменять в коде к моменту C

| Место | Сейчас | Цель |
| --- | --- | --- |
| `release::TARGET_BETA_VERSION` | `3.8.0-rust` | реальный номер версии |
| `release::NATIVE_BETA_PROFILE` | `zabor-desktop-native-beta` | `zabor-desktop` (только на этапе C) |
| `Profile::default_path` | `zabor-desktop-native-beta` | `zabor-desktop` |
| Автозапуск | `zabor-native-beta` | `zabor` |
| Установщик | нет | подписанный NSIS/MSI с appId `com.zabor.desktop` |
| Attestation | `dev`/`official` из окружения | официальная сборка с подписью |

Пункты таблицы нельзя менять по одному: смена профиля без миграции теряет
доступ к истории, смена appId без удаления Electron ломает ярлыки и updater.

## 5. Порядок ближайших шагов

1. Собрать и проверить developer-сборку (`--developer`, профиль
   `zabor-desktop-native-dev`) — это то, что можно запускать уже сейчас.
2. Закрыть подписи и установщик для beta-канала native.
3. Сделать экспорт в Electron-буфере и UI-импорт в native.
4. Прогнать два устройства, hotplug/AEC, SFU/RC, длинные сессии.
5. Только затем переименование профиля/версии и удаление суффиксов.

## 5.1. Developer-сборка для локальной проверки

Она не является ни установщиком релиза, ни приёмкой установки, но позволяет
запустить настоящий клиент, а не preview:

```text
native.bat build --release
```

Затем `zabor-native.exe --developer` (профиль `zabor-desktop-native-dev`,
автозапуск `zabor-native-dev`). Для допуска к своему серверу нужен
`ZABOR_CLIENT_SECRET` Оператора; значение задаётся в окружении и не
записывается в репозиторий.

Локальный установщик для проверки собирается отдельно из
`scripts/native/packaging/dev-installer.cs` и кладёт файлы в
`%LOCALAPPDATA%\ZaborDev`, ярлык `zabor (dev)`. Он не подписан, не публикуется
и не меняет профили stable/beta.

## 6. Границы

Этот документ не утверждает, что миграция реализована. Сейчас существуют:
CLI-импорт, отдельные профили и архив legacy. Автоматического перехода,
UI-импорта, подписанного установщика и рабочего updater пока нет.
